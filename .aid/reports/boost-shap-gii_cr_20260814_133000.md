    <finding id="F1" severity="major" category="assumptions">
      <location file="src/boost_shap_gii/shap_utils.py" lines="986-1014" />
      <description>
        SHAP bootstrap ignores group correlation under cv_strategy="group".

        When cv_strategy="group", GroupKFold places all members of the same group into the same
        validation fold. Their OOF SHAP values are computed by the same fold model, inducing
        within-group correlation (same model parameters, correlated feature vectors, correlated
        outcomes). The SHAP bootstrap in _run_bootstrap_pipeline() resamples individual rows i.i.d.
        (line 1014: rng.integers(0, n_samples, size=(n_boot, n_samples))), treating all observations
        as exchangeable. This is the naive bootstrap under cluster structure.

        The issue is asymmetric with respect to the exceedance test: shadow features are
        column-permuted, which breaks within-group correlation for shadow SHAP values. Therefore:
        (a) real-feature bootstrap M/V/GII distributions are too concentrated (variance underestimated),
        while (b) shadow-feature distributions are correctly estimated. The exceedance test (real >
        shadow max?) becomes anti-conservative: the concentrated real-feature distribution exceeds
        the shadow max more consistently than warranted, producing p-values that are too small.
      </description>
      <evidence>
        shap_utils.py:1014 uses rng.integers(0, n_samples, ...) for non-inference bootstrap,
        treating rows as i.i.d. regardless of cv_strategy. The cluster_ids mechanism (lines 989-1012)
        exists for inference mode but is not activated for predict-mode (training) even when
        cv_strategy="group". Shadow permutation (_block_permute_shadow in utils.py:39-88) applies
        independent or block-permuted column shuffles that destroy within-group observation correlation.
        indiv_reports.py:362-363 already handles this correctly by falling back to KFold for group CV
        bootstrap, with explicit documentation: "bootstrap resampling breaks group structure."
      </evidence>
      <literature>
        Cameron, Gelbach & Miller (2008, Review of Economics and Statistics 90(3):414-427):
        demonstrate that failure to cluster the bootstrap at the appropriate level under
        intra-cluster correlation produces CIs with below-nominal coverage and tests with
        above-nominal rejection rates. Effect grows with intra-cluster correlation and cluster
        size; most severe when number of clusters is moderate (10-50). Davison & Hinkley (1997,
        Bootstrap Methods and Their Application, ch. 3) provide the general theory for cluster
        bootstrap. Field & Welsh (2007, JRSS-B 69(3):369-390) establish conditions under which
        the cluster bootstrap is consistent.
      </literature>
      <impact>
        Potential false discoveries (anti-conservative significance calls) when cv_strategy="group"
        with strongly correlated groups. Severity scales with within-group correlation strength
        and ratio of mean group size to total N. For datasets with many small groups
        (e.g., 100 groups of size 5), impact is modest. For datasets with few large groups
        (e.g., 5 groups of size 100), impact could be substantial. The stability threshold
        (stab_thresh >= 2) and BH-FDR correction provide secondary guard rails but do not
        fully compensate.
      </impact>
      <recommendation>
        Before releasing cv_strategy="group", implement a cluster-bootstrap path in the
        non-inference SHAP bootstrap that resamples at the group level when cv_strategy="group".
        The group_column values could be threaded through the SHAP pipeline context (predict.py
        context dict, passed to run_shap_pipeline) and used as cluster_ids, reusing the existing
        cluster-bootstrap machinery (lines 989-1012). This requires: (1) passing groups through
        the predict.py SHAP context, (2) activating cluster_ids in _run_bootstrap_pipeline for
        non-inference mode when groups are present, (3) building the cluster_to_rows mapping from
        group labels rather than from observation indices. Alternatively, document as a known
        limitation with quantitative guidance (e.g., "group-level bootstrap recommended when
        n_groups < 50 or mean group size > 5").
      </recommendation>
    </finding>

    <finding id="F4" severity="minor" category="robustness">
      <location file="src/boost_shap_gii/utils.py" lines="206-239" />
      <description>
        _RepeatedGroupKFold uses round-robin group assignment, diverging from sklearn's
        GroupKFold greedy algorithm.

        The single-repeat case (n_repeats=1) uses sklearn's GroupKFold via _GroupKFoldWrapper,
        which assigns groups to folds using a greedy algorithm that minimizes fold-size imbalance
        (assigns the next-largest group to the currently smallest fold). The multi-repeat case
        (n_repeats > 1) uses _RepeatedGroupKFold, which permutes the group ordering and assigns
        groups round-robin (i % n_splits). For datasets with heterogeneous group sizes, round-robin
        on a random permutation produces different (and generally less balanced) fold-size
        distributions than the greedy algorithm.
      </description>
      <evidence>
        _GroupKFoldWrapper (utils.py:195-205) delegates to sklearn.model_selection.GroupKFold,
        which uses a greedy assignment. _RepeatedGroupKFold (utils.py:208-239) implements:
          perm = rng.permutation(len(unique_groups))
          for i, g in enumerate(unique_groups[perm]):
              group_to_fold[g] = i % self.n_splits
        This is round-robin on permuted groups, not greedy. The first repeat of
        _RepeatedGroupKFold may produce different folds than _GroupKFoldWrapper even with
        the same groups.
      </evidence>
      <literature>
        sklearn source for GroupKFold._make_test_folds (v1.5): groups are sorted by total
        sample count and assigned greedily to the fold with the fewest samples. This is a
        variant of the multiprocessor scheduling heuristic (Graham 1966).
      </literature>
      <impact>
        Inner CV with n_inner_repeats > 1 may have different fold-size distributions than
        outer CV with n_repeats=1. For datasets with highly variable group sizes, this could
        affect Optuna tuning quality (some inner folds may be very small, producing high-variance
        score estimates). Practical impact is modest for most datasets.
      </impact>
      <recommendation>
        Two options: (1) Implement the greedy assignment algorithm in _RepeatedGroupKFold
        (match sklearn's behavior per repeat). (2) Document the behavioral difference and
        add a diagnostic warning when the max/min fold-size ratio exceeds 2.0 within any
        repeat of _RepeatedGroupKFold. Option (2) is simpler and adequate.
      </recommendation>
    </finding>

    <finding id="F5" severity="minor" category="robustness">
      <location file="src/boost_shap_gii/train.py" lines="526-548" />
      <description>
        No validation that n_inner_repeats is compatible with the number of unique inner groups.

        When cv_strategy="group" with n_inner_repeats > 1, _RepeatedGroupKFold permutes groups
        and assigns them round-robin. If the number of unique groups in the inner (outer-training)
        fold is close to or equal to inner_cv_folds, the number of distinct group-to-fold
        arrangements is limited (at most n_groups! / (n_groups/n_folds)!^n_folds permutations
        produce distinct assignments). With, e.g., 5 inner groups and 5 inner folds, every
        permutation produces the same partition (each group in its own fold), making repeats
        entirely redundant. No warning is emitted.
      </description>
      <evidence>
        run_optuna_tuning (train.py, uncommitted) accepts groups and n_inner_repeats. The
        inner_cv is created via get_cv_splitter with n_repeats=n_inner_repeats. For group CV,
        this returns _RepeatedGroupKFold. No check on len(np.unique(inner_groups)) vs.
        inner_cv_folds exists. The existing warning at line 540 only checks n_inner_repeats > 10.
      </evidence>
      <literature>
        Vanwinckelen & Blockeel (2012, Belgian-Dutch AI Conference): demonstrate diminishing
        returns from repeated CV; the variance reduction is proportional to 1/n_repeats only
        when each repeat produces genuinely distinct fold compositions.
      </literature>
      <impact>
        Users may configure n_inner_repeats > 1 expecting variance reduction but receive
        minimal or zero benefit, wasting computation (n_inner_repeats * inner_cv_folds *
        n_trials total fits). Misleading total-fits warning (line 544-548) would report a
        high fit count that is largely redundant.
      </impact>
      <recommendation>
        Add a check in run_optuna_tuning: if cv_strategy="group" and groups is not None,
        compute n_unique_inner = len(np.unique(groups)) and warn if n_unique_inner <
        2 * inner_cv_folds (below this threshold, repeat diversity is severely constrained).
      </recommendation>
    </finding>

    <finding id="F6" severity="minor" category="robustness">
      <location file="src/boost_shap_gii/utils.py" lines="161-165" />
      <description>
        stratify_labels_for_regression may silently reduce bin count.

        pd.qcut(..., duplicates='drop') can produce fewer bins than n_splits when the target
        has many tied values (e.g., zero-inflated outcomes, discrete-valued regression targets,
        ordinal outcomes treated as continuous). The fallback to pd.cut (equal-width bins) may
        also produce poor stratification for highly skewed targets (most observations in one bin).
        No diagnostic message is emitted when the actual bin count diverges from n_splits.
      </description>
      <evidence>
        stratify_labels_for_regression (utils.py:161-165):
          try: return pd.qcut(y, q=n_bins, labels=False, duplicates='drop')
          except ValueError: return pd.cut(y, bins=n_bins, labels=False)
        pd.qcut with duplicates='drop' silently reduces the number of bins when quantile
        boundaries coincide. The returned Series has fewer unique values than n_bins.
        StratifiedKFold then stratifies on the reduced bin set, producing coarser balance
        than intended.
      </evidence>
      <literature>
        This is a known behavior of pandas qcut (pandas documentation: "If bin edges are not
        unique, raise ValueError or drop non-uniques with duplicates='drop'"). The impact on
        stratified CV quality depends on how many bins are dropped.
      </literature>
      <impact>
        For targets with many ties (e.g., >50% of values at a single level), stratified CV
        may degenerate to near-unstratified behavior. The user would not know this occurred.
        Practical impact is limited because such targets are uncommon in the pipeline's
        primary use case (continuous outcomes).
      </impact>
      <recommendation>
        After the qcut/cut call, check the actual number of unique bins and emit a warning
        if it is less than n_bins: e.g., "[WARNING] Stratified regression CV: only {actual}
        of {requested} target bins achieved; stratification may be coarse."
      </recommendation>
    </finding>

    <finding id="F7" severity="note" category="inferential_calibration">
      <location file="src/boost_shap_gii/shap_utils.py" lines="1195-1198" />
      <description>
        BH-FDR assumes PRDS for SHAP-based test statistics.

        The FDR correction uses method='fdr_bh' (Benjamini-Hochberg 1995), which controls FDR
        at the nominal level under PRDS (positive regression dependence on subsets; formally
        established in Benjamini & Yekutieli 2001). The SHAP-based exceedance statistics share
        common bootstrap samples and common training data, producing complex inter-test dependence.
        The PRDS condition is plausible (features competing against common noise tend to be
        positively correlated in their exceedance behavior) but is not formally verified. Under
        arbitrary (non-PRDS) dependence, BH may be slightly liberal (actual FDR exceeds nominal).
      </description>
      <evidence>
        _nan_safe_fdr (shap_utils.py:1168-1198) calls multipletests(p_vals, alpha=alpha_val,
        method='fdr_bh'). Three independent BH calls are made (sig_M, sig_V, sig_GII), each
        receiving the full pooled p-value vector. INPUT_SPECIFICATION.md correctly documents
        this as "Benjamini-Hochberg FDR (BH-FDR)."
      </evidence>
      <literature>
        Benjamini & Hochberg (1995, JRSS-B 57(1):289-300): original BH procedure, proved under
        independence. Benjamini & Yekutieli (2001, Annals of Statistics 29(4):1165-1188): extended
        to PRDS and to arbitrary dependence (with a log(m) correction factor, i.e., BY-FDR).
        The distinction matters: BH under arbitrary dependence has actual FDR up to ~alpha * log(m),
        where m is the number of tests.
      </literature>
      <impact>
        Minimal for the current pipeline: the three-family structure (independent BH calls per
        family) limits the effective m within each family. For a typical dataset with ~50 features
        and ~1225 interactions, the largest family has ~1275 tests; log(1275) ~ 7.2. Under worst-case
        non-PRDS, actual FDR could be up to ~7x nominal. However, PRDS is plausible here, making
        this a theoretical rather than practical concern. The stability threshold (stab_thresh >= 2)
        provides an independent filter that is not affected by dependence assumptions.
      </impact>
      <recommendation>
        No action required. The choice of BH-FDR is defensible and consistent with standard
        practice. Consider documenting the PRDS assumption explicitly in INPUT_SPECIFICATION.md
        Section 3 for transparency. Optionally, expose method='fdr_by' as a config option
        (e.g., shap.bootstrapping.fdr_method) for users who require conservative FDR control
        under arbitrary dependence.
      </recommendation>
    </finding>

    <finding id="F8" severity="note" category="reproducibility">
      <location file="src/boost_shap_gii/train.py" lines="939-940" />
      <description>
        CatBoost multi-thread non-determinism is a known reproducibility limitation.

        CatBoost's multi-threaded training produces non-deterministic results because
        floating-point summation order varies across threads. The pipeline sets thread_count
        from config.execution.n_jobs, which defaults to os.cpu_count(). Results therefore
        vary across machines with different CPU counts even with identical random seeds.
        This is already documented in INPUT_SPECIFICATION.md but is noted here for completeness.
      </description>
      <evidence>
        train.py:939 injects thread_count = n_jobs into best_params. n_jobs defaults to
        os.cpu_count() (utils.py:420). CatBoost documentation: "Results may differ with
        different thread_count values due to floating point summation order."
        INPUT_SPECIFICATION.md documents this limitation.
      </evidence>
      <literature>
        CatBoost documentation (catboost.ai): "Training results depend on the number of threads
        used for training." Goldberg (1991, ACM Computing Surveys 23(1):5-48): "What Every
        Computer Scientist Should Know About Floating-Point Arithmetic" establishes why
        summation order affects results.
      </literature>
      <impact>
        Exact numerical reproducibility across hardware configurations is not achievable.
        This is a fundamental limitation of multi-threaded gradient boosting, not specific
        to this pipeline. The pipeline's simulation study (separate project) addresses this
        with a dedicated determinism drift study.
      </impact>
      <recommendation>
        No action required. The limitation is already documented. The 600-run determinism
        drift study planned for the simulation project (MEMORY.md Session 10) will quantify
        the practical magnitude of this effect.
      </recommendation>
