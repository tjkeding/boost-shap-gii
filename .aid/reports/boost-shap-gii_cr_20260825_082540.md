    <finding id="F1" severity="major" category="robustness">
      <location file="src/boost_shap_gii/indiv_reports.py" lines="703-706, 1032-1036" />
      <description>
        The individual-level SHAP CI bootstrap in indiv_reports.py obtains cluster IDs from config["data"]["cluster_id_col"], an undocumented config key that is never populated by fill_config_defaults(), never appears in example_config_advanced.yaml, and is not documented in INPUT_SPECIFICATION.md. The GII bootstrap pipeline in shap_utils.py correctly obtains group structure from config["modeling"]["group_column"] (via the shap context populated by predict.py:515-519 and infer.py:1463-1469). This config key mismatch means that when cv_strategy="group" is active, population-level GII bootstrap uses cluster-aware resampling (correct) while individual-level SHAP CIs use i.i.d. resampling (anti-conservative under within-group correlation).
      </description>
      <evidence>
        indiv_reports.py:703-706 (training mode):
          cluster_col = config.get("data", {}).get("cluster_id_col")
          if cluster_col and cluster_col in X_train.columns:
              cluster_ids = X_train[cluster_col].values

        indiv_reports.py:1032-1036 (inference mode): identical pattern.

        Contrast with predict.py:515-519:
          if cv_strategy == "group" and group_column is not None and group_column in df_raw.columns:
              shap_ctx["groups"] = df_raw[group_column].values

        grep for "cluster_id_col" across utils.py, example_config_advanced.yaml, and INPUT_SPECIFICATION.md returns zero hits outside of indiv_reports.py, confirming the key is never populated.
      </evidence>
      <literature>
        Cameron, Gelbach &amp; Miller (2008): cluster-robust bootstrap requires resampling at the cluster level. i.i.d. resampling under within-group correlation underestimates variance, producing anti-conservative CIs whose coverage degrades with increasing ICC and mean cluster size. Already cited in the pipeline's cluster bootstrap implementation (shap_utils.py).
      </literature>
      <impact>
        When a user configures cv_strategy="group" with group_column, individual-level SHAP CIs (both training and inference modes) are anti-conservative. The degree of anti-conservatism scales with the intraclass correlation coefficient and mean cluster size. A peer reviewer examining the pipeline's internal consistency between population-level and individual-level inference would flag this as a methodological gap.
      </impact>
      <recommendation>
        Replace the config["data"]["cluster_id_col"] lookup in both locations (indiv_reports.py:703-706 and 1032-1036) with config["modeling"]["group_column"], mirroring the pattern used by the rest of the pipeline. The existing KFold fallback for group CV within the bootstrap loop (indiv_reports.py:362-364) already correctly handles the downstream implications, so the fix is localized to how cluster_ids is obtained.
      </recommendation>
    </finding>

    <finding id="F2" severity="minor" category="reproducibility">
      <location file="src/boost_shap_gii/predict.py" lines="318-323" />
      <description>
        When the transformations API is active, predict.py reconstructs each fold's fold_meta by re-calling transform_module.input_transform() (line 321), rather than loading from the fold_transform_metadata.json artifact that train.py persisted during training. In contrast, infer.py correctly loads the persisted metadata (infer.py:287-289). This creates an inconsistency in the fold_meta sourcing contract: the artifact exists specifically to provide a single-write-point for transformation parameters, but predict.py bypasses it.
      </description>
      <evidence>
        predict.py:321:
          _, _, fold_meta = transform_module.input_transform(
              df_raw, train_idx_k, val_idx, outcome_col, tx_info.get("params", {}))

        infer.py:287-289:
          fold_meta_path = os.path.join(train_dir, "fold_transform_metadata.json")
          with open(fold_meta_path) as f:
              _fold_transform_meta = json.load(f)
      </evidence>
      <literature>
        Reproducibility best practice: transformation parameters computed at training time should be persisted and reloaded, not re-derived, to avoid dependence on determinism of the transform function across invocations. The fold_transform_metadata.json artifact was introduced in v1.5.0 precisely for this purpose (decoupling infer.py from the training data file).
      </literature>
      <impact>
        Functionally correct for deterministic, state-free transforms. Fails if input_transform uses stochastic elements (e.g., robust subsample estimation) or depends on external state (environment variables, filesystem state). The resulting back-transformed predictions could silently differ from training-time expectations. A reviewer examining the transformations API contract would note the asymmetry between predict.py and infer.py.
      </impact>
      <recommendation>
        Modify predict.py to load fold_transform_metadata.json and index into it by fold, mirroring infer.py's approach. This closes the contract gap and ensures back-transformation parameters are always sourced from the single-write-point artifact.
      </recommendation>
    </finding>

    <finding id="F3" severity="minor" category="inferential_calibration">
      <location file="src/boost_shap_gii/infer.py" lines="500" />
      <description>
        The permutation test resolution floor differs between predict and infer modes. predict.py applies n_perm = max(n_boot, 1000), enforcing a minimum of 1000 permutations regardless of the user's n_boot setting. infer.py uses n_perm = n_boot with no floor.
      </description>
      <evidence>
        predict.py:441: n_perm = max(config["shap"]["bootstrapping"]["n_boot"], 1000)
        infer.py:500:   n_perm = n_boot
      </evidence>
      <literature>
        Permutation test resolution determines the minimum achievable p-value (1/(n_perm+1)). At n_perm=500, the minimum non-zero p-value is ~0.002; at n_perm=1000, it is ~0.001. The floor in predict.py ensures adequate resolution for effects near the significance threshold. The absence of a matching floor in infer.py creates an undocumented behavioral asymmetry.
      </literature>
      <impact>
        The default n_boot is 10000, so the floor rarely binds. Under low n_boot settings (e.g., 500 for exploratory runs), infer-mode permutation tests have coarser p-value resolution than predict-mode tests. The direction is conservative for infer mode (coarser resolution makes significance harder to achieve), but the inconsistency is an unintentional asymmetry that a reviewer could flag.
      </impact>
      <recommendation>
        Apply the same floor in infer.py: n_perm = max(n_boot, 1000). This harmonizes the two modules and ensures adequate permutation test resolution regardless of the user's n_boot setting.
      </recommendation>
    </finding>
