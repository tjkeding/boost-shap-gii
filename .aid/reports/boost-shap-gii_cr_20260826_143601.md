    <finding id="F2" severity="minor" category="validity">
      <location file="src/boost_shap_gii/indiv_reports.py" lines="635-655" />
      <description>shap_scale_factor is not applied to individual-level SHAP values in indiv_reports.py. When back_transform_shap=true, the global SHAP pipeline (shap_utils.py:971-976) multiplies SHAP values by shap_scale_factor to express them on the raw-outcome scale. However, generate_indiv_reports() neither receives nor applies shap_scale_factor. Individual SHAP point estimates, CIs, and interaction values are emitted on the transformed scale, creating a scale inconsistency with global SHAP outputs.</description>
      <evidence>grep confirms shap_scale_factor is completely absent from indiv_reports.py. The function signature (lines 635-655) has no shap_scale_factor parameter. The output assembly (lines 1036+) writes point_shap directly to parquet without scaling. shap_utils.py:971-976 applies `SHAP_vals = SHAP_vals * shap_scale_factor` for global SHAP.</evidence>
      <literature>Lundberg &amp; Lee (2017) linearity axiom: for an affine transformation y_raw = alpha * y_transformed + beta, SHAP_raw = alpha * SHAP_transformed. This scaling must be applied consistently across all SHAP outputs (global and individual) for interpretive coherence.</literature>
      <impact>For additive residualization (current use case), shap_scale_factor = 1.0, so the omission has zero effect. For multiplicative affine transforms (supported but currently unused), individual SHAP values and CIs would be on a different scale than global SHAP values, producing inconsistent feature importance rankings between global and individual reports.</impact>
      <recommendation>Thread shap_scale_factor through the generate_indiv_reports signature and apply it to point_shap, all CI bounds (main and interaction), and prediction back-transforms before output assembly. This ensures global and individual SHAP reports are always on the same scale when the user opts into back_transform_shap.</recommendation>
    </finding>

    <finding id="F4" severity="minor" category="validity">
      <location file="src/boost_shap_gii/predict.py" lines="493-505" />
      <location file="src/boost_shap_gii/indiv_reports.py" lines="480-632" />
      <description>Bootstrap conditioning uses a globally-fit transform rather than per-fold transforms, creating an estimand mismatch with the deployed models. predict.py (lines 493-505) calls input_transform(df_raw, all_idx, all_idx, ...) to produce a single globally-transformed y_bootstrap. The deployed fold models were each trained on fold-specific transforms (fit on ~80% of data per fold). Bootstrap models are therefore trained on a systematically different estimand than the deployed models they approximate. CatBoost's internal parameters (ordered target statistics, tree structure, leaf values) are re-estimated per bootstrap iteration, but the transform coefficients are not, creating an asymmetry in the re-estimation structure.</description>
      <evidence>predict.py:499 `y_transformed, _, _ = transform_module.input_transform(df_raw, all_idx, all_idx, ...)` fits the residualization on the full dataset. The `_` discards the global fold_meta. orchestrate_bootstrap_cache (indiv_reports.py:480-632) receives this globally-transformed y_bootstrap and trains B x K models on subsets of it. Each deployed model_fold_k.cbm was trained on fold-k-specific residuals (train.py:1013-1018).</evidence>
      <literature>Davison &amp; Hinkley (1997), ch. 5: conditional bootstrap conditions on nuisance parameters. The current design conditions on a global transform; the proposed design conditions on per-fold transforms, aligning the bootstrap estimand with the deployed estimand at every level. For stable linear residualization at large N, the global-fit approximation introduces O(1/sqrt(N)) systematic bias, which is negligible. For small N or unstable transforms, the bias may be material.</literature>
      <impact>Systematic (not random) shift between bootstrap and deployed residuals. For typical use cases (large N, additive linear residualization), the practical impact on CI widths is negligible. For small-N studies or transforms with coefficient instability, the bias could inflate or deflate CIs.</impact>
      <recommendation>Implement per-fold-per-bootstrap transforms: (1) serialize df_raw and transform module path to temp files at cache creation; (2) each worker loads df_raw and transform module, calls input_transform with its fold's train_idx/val_idx, trains CatBoost on fold-specific y_train, discards fold_meta after training; (3) only .cbm files are persisted (no per-bootstrap metadata storage needed); (4) compute per-fold shap_scale_factor (alpha) during training and store in each entry of fold_transform_metadata.json; (5) validate cross-fold alpha consistency; (6) transform_config.json remains a global artifact. Cost: B x K additional input_transform calls (sub-millisecond each for linear regression), negligible relative to CatBoost training time.</recommendation>
    </finding>
